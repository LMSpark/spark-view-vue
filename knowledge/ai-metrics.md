# AI 编码效果度量

### 为什么要度量

行业实证数据（GitClear 1.5亿行、Faros AI、arxiv 差分研究）表明：
- AI工具让开发者自评效率+20%，但对照实验实测-19%
- 代码流失率（30天内被改写/回滚的比例）从3.3%升至5.7-7.1%
- AI代码的PR审查时间增加50-91%
- 30天流失率上升 → 90天事故率必然跳升（已验证的前导指标）

不度量就无法知道AI在你的项目里是帮忙还是帮倒忙。

### 度量什么

**只盯一个核心指标：代码存活率**

代码存活率 = 1 - 代码流失率 = 30天后仍未被改写或回滚的代码占比

这是行业验证过的最可靠前导指标。存活率高说明AI产出的代码质量好；存活率低说明审查没拦住问题代码。

辅助指标（可选）：

| 指标 | 含义 | 采集方式 |
|------|------|---------|
| 返工次数 | 单个任务在阶段6被中止并回滚的次数 | 协议执行日志 |
| 审查轮次 | 方案从提交到通过经历了几轮修订 | 阶段5记录 |
| 知识沉淀率 | 完成的任务中有多少产出了knowledge条目 | knowledge/目录增长 |
| 人工干预率 | AI在阶段2-6中被用户纠正的次数 | 会话记录 |

### 怎么记录

每次用AI完成一个任务后，在 `notes/ai-code-metrics.md` 中追加一条记录：

```markdown
### [日期] [任务名]

- **复杂度**：简单/中等/复杂
- **总耗时**：从阶段1到阶段7的总时长（分钟）
- **返工次数**：阶段6中止+回滚了几次
- **审查轮次**：阶段5修订了几轮才通过
- **30天存活**：（30天后回填）代码是否仍在、是否被改写
- **知识沉淀**：是否产出了knowledge条目（是/否）
- **人工干预**：在哪些阶段纠正了AI的判断
```

30天后回填"30天存活"字段——用 `git log` 检查AI修改的文件是否被后续提交改过。

### 怎么用数据

- **月度回顾**：统计当月所有任务的存活率、平均返工次数、平均审查轮次
- **按复杂度分组**：简单任务的AI效果可能远好于复杂任务——这决定你在哪些场景该用AI、哪些场景该自己写
- **趋势判断**：如果knowledge沉淀率上升+存活率上升，说明学习闭环在生效
- **停止信号**：如果某类任务的30天存活率持续低于70%，说明AI在这类任务上不可靠，应该改为自己写或加强阶段1的研读深度

### 行业基准

| 指标 | 较差 | 一般 | 优秀 |
|------|------|------|------|
| 30天代码存活率 | <75% | 75-85% | >85% |
| 变更失败率 | 上升 | 持平 | 下降 |
| 单任务平均返工次数 | >2 | 1-2 | 0 |
| 审查轮次 | >3 | 1-3 | 1 |
| 知识沉淀率 | <20% | 20-50% | >50% |

### 与7阶段协议的对应

| 流失率根因 | 协议防线 | 对应度量 |
|-----------|---------|---------|
| AI没读代码就写方案 | 阶段1深度研读+研读复述 | 审查轮次（研读质量差→审查多轮） |
| 需求理解偏差 | 阶段2反向提问 | 返工次数（理解偏差→实施后回滚） |
| AI自由发挥 | 阶段5 HARD-GATE | 返工次数（方案不准→实施时中止） |
| 审查走形式 | 阶段6最小闭环+首次必验证 | 30天存活率（审查质量差→后续被改） |
| 重复犯同样错误 | 阶段7知识沉淀 | 知识沉淀率 |
| 跨会话上下文丢失 | EPSS委派协议 | 返工次数（上下文丢失→重复踩坑） |
